Database shadowing proxy

ShadowDB

Mirrors live database traffic to a shadow database, so schema migrations and chaos tests meet real load before production does.

  • Java
  • Netty
  • Kafka
  • PostgreSQL
  • MongoDB
  • Prometheus
  • Grafana
Live model Simulated traffic, real benchmark figures
50.2Krequests a second
3.0 msadded latency
100%traffic mirrored

    The problem

    Schema changes and failure drills are risky to rehearse on staging data that looks nothing like production traffic.

    What I built

    A Netty proxy in front of the primary database that copies every live query to a shadow. The shadow can run a new schema, or be broken on purpose, and the application never notices.

    Results

    Try it: apply a migration and watch the shadow’s latency split from the primary. Then kill the shadow. Production traffic keeps flowing.

    The problem

    Financial APIs break at the edges: odd amounts, closed accounts, two requests landing at once. Those are the cases that rarely get tested.

    What I built

    A gateway over five mock services (accounts, payments, cards, loans, FX) with contract tests in JUnit 5 and REST Assured, run by Jenkins. A reusable test-data factory keeps each test short, and Mockito isolates every service.

      The problem

      Booking has two hard parts: searching a huge catalogue quickly, and not losing a guest’s dates when a payment fails halfway through.

      The problem

      GraphQL makes nested queries easy to write and easy to make slow: every trip, day and stop can fire its own database call.

      What I built

      A Kotlin and Spring for GraphQL schema for trips and wishlists, with DataLoader batching each level into one query. Itinerary ideas come from an LLM API through Spring AI, with responses cached in Redis.
